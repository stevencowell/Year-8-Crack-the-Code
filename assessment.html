Source-grounded student guide

Assessment

Design, code, test and evaluate a ThinkerShield alarm or alert system that protects something you care about.

What you are being asked to do

The supplied unit materials establish the final challenge and its fixed hardware. Your outputs must change according to data from the available inputs. The site does not invent current administrative arrangements.

Design and communicate

  • identify the need, user and protected item
  • write testable criteria within the fixed hardware constraints
  • communicate the signal path using a pin map, IPO, pseudocode and flowchart

Produce and evaluate

  • build a working sketch from the authorised activity pathway
  • test normal, alert, boundary and recovery conditions
  • debug systematically and evaluate against evidence
Current arrangements: due date, marks, rubric, lesson timing, collaboration rules, file name, Drive location and Classroom submission route are all Teacher to confirm.

Evidence checkpoints

CheckpointEvidence you can prepare here

ProductionNamed code record, teacher feedback if authorised and final build notes.
TestingExpected versus actual results, boundary and recovery cases, debugging log.
EvaluationCriterion-by-criterion judgement, precise improvements and learning reflection.

Use the criteria as checkpoints, not decoration

A strong criterion names an observable behaviour and a way to test it. “When the LDR reaches the calibrated alert range, the buzzer on pin 3 and red LED respond, then return to the normal state when light returns” is testable. “It works well” is not.
